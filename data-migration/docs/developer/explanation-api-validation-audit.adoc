= Explanation: API-level validation and migration compliance
:toc: left

An audit of every DEMOS API-level validation check that migrated data can trip,
split by *when* it fires, with each migration data category mapped to the checks
it violates. Audience: a developer deciding whether a given DEMOS rule is a
load-time blocker, a read-time breaker, or a post-cutover workflow problem, plus
the reader who needs to know which of the audit's fixes actually shipped. By the
end you will know why phantom `Completed` phases do not block anything, why
`validateInputDates` is the one rule that does, and what is still owed by the
DEMOS server.

[IMPORTANT]
====
*Audit accurate; fixes mostly shipped, with a live cross-repo gap (as of
2026-07-30).* Every migration-repo fix this audit proposed is now implemented
(see <<build-queue>>), and the DEMOS `is_migrated_from_pmda` flag shipped on
`application`. The two DEMOS-side validator skips that the audit called
mandatory -- <<demos-requests,4B.2>> (phase completion) and
<<date-skip,4B.3>> (the date path) -- are *not* implemented:
`server/src/model/applicationPhase/validatePhaseCompletion.ts` calls
`checkPhaseCompletionRules` unconditionally, and
`server/src/model/applicationDate/validateAndUpdateDates.ts` calls
`validateInputDates` unconditionally. Until they land, operators cannot advance
or date-edit a migrated demonstration.
====

The audit was performed 2026-07-20 against the DEMOS server checkout, tracing
the phase-date mapping and the `is_migrated` exemption. It reconciles
xref:../sme/reference-sme-signoff-2026-07-20.adoc[the SME sign-off ledger] and
xref:reference-cross-cutting-derivations.adoc[the cross-cutting derivations

only*; DEMOS-server changes are written as ready-to-hand-off cross-repo
requests, because this repo cannot merge them.

== What this page is not

This page is the *audit*: an enumeration of the DEMOS rules, when each fires,
and the disposition of each against migrated data. It is deliberately
complementary to
xref:explanation-api-validator-conformance.adoc[conformance to the DEMOS API
validator], which is the *design record* for the conformance harness -- how the
migration will re-run the real TypeScript validators against the loaded
database, why that harness lives in the DEMOS repo rather than here, and where
its gate slots into the pipeline.

Read that page for the mechanism. Read this page for the rule-by-rule ledger,
the tier classification, and the shipped guards that quantify each residual.
Where the two overlap -- the date and phase rules of its bucket B -- this page
supplies the concrete violation modes and the SQL transcriptions that count
them.

[[surfaces]]
== The two enforcement surfaces

DEMOS enforces data validity on two surfaces that fire at completely different
times. Conflating them is the root of the mis-scoping in the SME ledger.

[mermaid]
....
flowchart TD
  L[migration load via pgloader and SQL] --> DB{DB constraints}
  DB -->|violated| ABORT[load aborts]
  DB -->|ok| ROW[migrated row in demos_app]
  ROW --> R{API read}
  ROW --> M{API mutate}
  R -->|resolver throws| BRK[record unviewable]
  M -->|validator throws| WF[cannot advance or edit]
....

*Surface A -- DB-enforced* (+server/src/model/**/*.prisma+,
`server/src/sql/functions.sql`, +server/src/model/migrations/**/migration.sql+):
NOT NULL, `@unique`/`@@unique`, `CHECK`, FK and composite-FK, `dbgenerated()`
defaults, and INSERT/AFTER-INSERT triggers. These fire on the *direct load* and
hard-abort it. The migration writes straight to Postgres, so it must satisfy or
work around every one of these.

*Surface B -- app-enforced* (TypeScript validators, GraphQL resolvers, Zod
report schemas): fire *only when the DEMOS API later reads or mutates* a
migrated row. The load bypasses them entirely; they become live only
post-cutover when operators touch migrated records.

=== Correction to the SME ledger

The SME sign-off ledger states that 97.7% of loaded demos "sit in a `Completed`
state that DEMOS's own rules call impossible" and that this *blocks*. Verified
against code, this is overstated:

* `checkPhaseCompletionRules` is invoked *only* from `completePhase`
  (`server/src/model/applicationPhase/completePhase.ts:24`), via
  `validatePhaseCompletion`.
* It validates *only the single phase named in the mutation*, and for prior
  phases calls `checkPriorPhaseCompleteForCompletion`, which checks
  `status === "Completed"` *and nothing else* -- no retroactive date or document
  re-check (`server/src/model/applicationPhase/checkPhaseFunctions.ts:98-112`).
* No read or list resolver re-runs any completion rule.

So phantom `Completed` phases do *not* break the load and do *not* break reads.
They bite on *forward workflow* (Tier 2). This reclassification is why the
phantom-phase item is downgraded from Tier 0 to Tier 2 below.

[[split-trigger-state]]
=== The DEMOS application triggers at load time (split state)

A second, decisive correction: the DEMOS *application triggers* are *not part of
the pinned schema the migration loads against*. The migration pins a Prisma DDL
snapshot (`reports/prisma_ddl.sha256` -> `state/prisma_ddl/<sha>.sql`) and loads
into that. That pinned artifact contains *no* `CREATE TRIGGER` or
`CREATE FUNCTION` -- `create_phases_and_dates_for_new_application`,
`generate_medicaid_chip_id_numbers`, and
`check_demonstration_primary_project_officer` live in
`server/src/sql/functions.sql`. Historically all three were deployed only by
DEMOS's `refreshDbObjects.ts` *after P5, before the flip* (after the load). See
xref:reference-prisma-ddl.adoc[the Prisma DDL pipeline] for the pin mechanism.

That is still true for *two* of them, but the medicaid/chip mint trigger split
off. DEMOS made `generate_medicaid_chip_id_numbers` *migration-aware*: gated on
the session GUC `demos_app.migration_mode`
(`server/src/sql/functions.sql:1645-1649`), it now *permits* an explicitly-set
`medicaid_id`/`chip_id` (legacy-preserve) and *mints* a `chip_id` from
`chip_id_number_seq` for any row left NULL, instead of unconditionally
`RAISE`-ing. So the migration now *deploys this one trigger itself* -- verbatim
from `functions.sql` via `lib.mint_trigger_deploy_sql` in `migration/lib.py`,
applied in `init_pg.run_ddl` (`migration/phases/init_pg.py`) right after the
pinned DDL -- and runs `build_app` with `demos_app.migration_mode='on'` as
txn-local `pre_sql` (`migration/phases/build.py`). The DuckDB/dbt reference
migration (`data/demos_data_tools/load_staged_data_to_demos_app.py`) uses the
identical pattern: `SET LOCAL demos_app.migration_mode='on'` wrapping the
application and demonstration inserts, with the mint trigger left enabled and
`create_phases_and_dates_for_new_application` disabled.

Consequence for Tier 0:

* *T0.1 (`chip_id` NOT NULL) is resolved by the mint trigger*, not by a schema
  change. The loader still writes NULL for rows with no legacy 21-W number; the
  trigger mints one on insert, so the NOT NULL column is satisfied and *no
  cross-repo DDL relaxation is required*. The loader floors `chip_id_number_seq`
  above every preserved legacy 21-W number *before* the inserts, so minted
  values cannot collide with a preserved `chip_id`
  (`demonstration_chip_id_key` UNIQUE).
* *T0.4 (medicaid/chip `RAISE EXCEPTION`) is neutralized by migration_mode*:
  with the GUC on, the trigger accepts the loader-supplied ids and only mints
  the NULLs.
* *T0.2 (phase and date auto-population)* and *T0.3 (primary Project Officer)*
  remain *avoided by deploy order*: their triggers stay ABSENT at load (the
  migration sets phases and roles itself) and are deployed only post-load by
  `refreshDbObjects.ts`.

*Preflight P0.9* (`migration/phases/preflight.py`) now enforces exactly this
split trigger state before `build_app`: `generate_medicaid_chip_id_numbers`
*MUST BE PRESENT*, while `create_phases_and_dates_for_new_application` and
`check_demonstration_primary_project_officer` *MUST BE ABSENT*. There is no
longer a genuine Tier-0 load-abort: T0.1 is covered by the mint trigger, and the
demonstration flow-trace harness (`tests/sql/test_demonstration_flow_live.py`)
proves the load completes with `chip_id` NOT NULL intact.

[[tier-2-dates]]
==== Why T2.2 is the dominant forward-workflow blocker

`validateInputDates` iterates every date present in the merged set and, for
each, runs timestamp, ordering and offset checks. Three of its failure modes are
guaranteed to trip on PMDA data:

. *Exact Eastern-boundary timestamps.* Every date value must be exactly Eastern
  midnight (`Start of Day`) or `23:59:59.999` (`End of Day`)
  (`checkInputDateIsStartOfDay` at `checkInputDateFunctions.ts:36`,
  `checkInputDateIsEndOfDay` at `:54`). Raw `phase_*_dt` values are not
  normalized to those boundaries.
. *Missing offset counterpart -> hard throw.*
  `getDateValueFromApplicationDateMap` throws when a required counterpart date
  is absent (`checkInputDateFunctions.ts:72-82`). The offset rules are
  bidirectional (for example `Completeness Review Due Date` and
  `State Application Submitted Date` at +/-15 days;
  `Federal Comment Period Start Date` and `Federal Comment Period End Date` at
  +/-30 days). If a migrated demo has one side but not the other -- common given
  the sparsity documented in the SME ledger -- the check for the present side
  throws.
. *Exact offsets.* Even with both sides present, legacy data almost never
  satisfies the exact 15, 30 or 1-day offsets. The server compares
  year/month/day only (`doYMDMatch`, `checkInputDateFunctions.ts:138`, throwing
  at `:157`).

Because `validateInputDates` runs over the *full existing date set* on *any*
phase completion or date edit, the very first attempt to advance or correct a
migrated demo throws -- independently of, and more pervasively than, the
phase-completion date requirement (T2.1). A DEMOS `is_migrated` skip on
`checkPhaseCompletionRules` alone is therefore insufficient; it must also cover
the date-validation path (see <<date-skip>>).

== Fixes and their status

[[migration-fixes]]
=== Migration-repo fixes

==== Tier-0 load-time guards

Per <<split-trigger-state>> the phase and primary-PO triggers are absent from
the pinned DDL at load (no PK collision T0.2, no primary-PO abort T0.3), and the
medicaid/chip trigger is migration-mode-aware: the migration deploys it and runs
`build_app` with `migration_mode='on'`, so it legacy-preserves the loader ids
and mints only NULL `chip_id` values (T0.1 and T0.4). The implemented guards
codify that split invariant fail-closed:

* *Preflight P0.8* (`migration/phases/preflight.py`) -- *informational* since the
  mint trigger resolves T0.1. Confirms `demos_app.demonstration.chip_id` exists
  and logs its nullability, but no longer `die`s on NOT NULL: the mint trigger
  generates a `chip_id` for the NULL rows during `build_app`, so the column may
  stay NOT NULL.
* *Preflight P0.9* (`migration/phases/preflight.py`) -- the
  split-trigger-state guard. `generate_medicaid_chip_id_numbers` *MUST BE
  PRESENT* (the migration deploys it; it mints NULL `chip_id` values on insert),
  while the other two DEMOS app triggers
  (`create_phases_and_dates_for_new_application`,
  `check_demonstration_primary_project_officer`) must be *absent* before
  `build_app`, catching the only residual risk: an operator applying
  `functions.sql` early.
* *Non-gating primary-PO parity check*
  (`sql/99_parity/57_primary_officer_missing.sql` plus
  `migration/phases/parity.py`) -- T0.3. Logs every loaded demonstration with no
  primary Project Officer to
  `reports/orphans/demonstration_missing_primary_officer.csv` for SME review;
  scoped to the full run (gated on
  `stg.demonstration_role_assignment_resolved`) so the app-layers idempotency
  harness treats it as a no-op. GREEN by decision: the post-load trigger never
  rejects these rows, so the gap is reported, not blocked.

[[date-normalization]]
==== T2.2 date normalization plus consistency guard

Normalize every emitted `date_value` to the exact Eastern boundary the target
`date_type` expects (Start-of-Day versus End-of-Day per
`DATE_TYPES_WITH_EXPECTED_TIMESTAMPS`):

[source,sql]
----
-- start-of-day date types
(date_value AT TIME ZONE 'America/New_York')::date::timestamp
  AT TIME ZONE 'America/New_York'                              AS date_value
-- end-of-day date types: same date at 23:59:59.999 America/New_York
((date_value AT TIME ZONE 'America/New_York')::date + interval '1 day'
  - interval '1 millisecond') AT TIME ZONE 'America/New_York'  AS date_value
----

This removes the timestamp-boundary throw (mode 1 of <<tier-2-dates>>). It
cannot fix missing offset counterparts or inexact legacy offsets without
fabricating data, so it pairs with the DEMOS skip (<<date-skip>>). The paired
*non-gating* parity view flags rows failing the boundary, the +/-15, +/-30 or
+/-1-day offsets, or a missing offset counterpart, so the residual dependent on
the DEMOS skip is quantified rather than silent.

[NOTE]
====
As shipped, the normalization lives one stage earlier than proposed: the tall
milestone view `sql/10_stg/27_application_milestone.sql` wraps every mapped
column in `migration.eastern_day_start()` or `migration.eastern_day_end()`
(both defined in `sql/00_init/03_helper_fns.sql`), and
`sql/20_app/36_application_date.sql` simply projects the already-normalized
values. The parity view shipped as
`sql/99_parity/60_application_date_consistency.sql`.
====

==== New non-gating parity checks

These close the visibility gaps the fact-net misses:

* A phantom-phase check reproduces the phantom-phase count as an enforced query
  -- `application_phase` rows carrying `Completed` whose phase's
  `datesMustExist` and `documentTypesMustExist` are unmet. This turns the SME
  ledger's 497-626 prose figure into a check. Shipped as
  `sql/99_parity/61_phantom_phase.sql`.
* A `chip_id` preload guard was proposed and then dropped: the
  chip_id-nullable assertion moved to Preflight P0.8 so it fail-closes *before*
  the load starts (fail-fast) rather than at the P6 parity gate. Status:
  RESOLVED, superseded by P0.8.

Both shipped parity views read a SQL transcription of the DEMOS validation
tables -- `sql/02_seeds_static/35_phase_completion_rule.sql` and
`sql/02_seeds_static/36_application_date_rule.sql`. The TypeScript is the source
of truth, not the transcription:
`tests/test_phase_completion_rule_drift.py` and
`tests/test_application_date_rule_drift.py` re-parse
`checkPhaseCompletionRules.ts`, `validateInputDates.ts` and `constants.ts` on
every run and fail if the two disagree. See
xref:howto-write-a-parity-check.adoc[how to write a parity check] for the
conventions these follow.

== Key considerations

* *Ordering.* No Tier-0 item blocks a full load: T0.1 and T0.4 are handled at
  load by the migration deploying the migration-mode-gated mint trigger and
  running `build_app` with `migration_mode='on'`
  (<<split-trigger-state>>), and T0.2 and T0.3 are avoided by the
  `refreshDbObjects.ts` deploy order, their triggers staying absent at load. No
  cross-repo DDL change is required before load. The Tier 2 items matter only
  once operators actively work migrated demos post-cutover.
* *Trigger deploy order is load-bearing.* The Tier-0 reprieve on T0.2 and T0.3
  rests entirely on `refreshDbObjects.ts` running *after* the load (P5 to flip),
  and on the migration deploying ONLY the mint trigger, not the whole
  `functions.sql`, before `build_app`. If that order ever changes, those items
  become live load-aborts again. Preflight P0.9 is the tripwire that fails
  closed if the triggers appear early; see
  xref:../operator/reference-gates-state.adoc[gates and `state/` files].
* *The date fix is split and neither half suffices alone.* Normalization removes
  one of three throw modes but cannot repair missing offset counterparts or
  inexact legacy offsets without fabricating data, so the DEMOS date-path skip
  (<<date-skip>>) is required, not optional.
* *No fabrication.* "X"-source dates stay absent under the exemption; the parity
  views quantify the residual rather than invent values.
* *Cross-repo dependency is on the critical path.* Everything Surface-B depends
  on the DEMOS validator skips. `is_migrated_from_pmda` has shipped on
  `application`, but nothing reads it in the date or phase validators yet, so
  the migration guards keep the gap visible and fail-closed rather than silently
  loading rows DEMOS will later reject.
