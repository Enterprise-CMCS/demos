= Explanation: Document and `document_type` migration
:toc: left

The design that was written for migrating PMDA's uploaded files into DEMOS's
`document` and `reference` tables: a crosswalk reconciliation plus a
metadata-only loader, with real file blobs deferred. Audience: a developer
picking the workstream up (here or in another repo) and an SME who needs to know
which document decisions were settled and which were never answered. By the end
you will know the target contract, every source family and its disposition, the
seven resolved decisions, and precisely why none of the loader shipped.

[IMPORTANT]
====
*Proposed -- not implemented (as of 2026-07-30).* There is no
`demos_app.document` loader in this repo: `sql/20_app/` contains no document
file and there is no `INSERT INTO demos_app.document` anywhere under `sql/`.
`sql/99_parity/30_scope_coverage.sql` records the entity as `OUT-OF-SCOPE` on an
operator decision dated 2026-07-27, because the byte-copy queue that would
supply `s3_path` has no producer. The crosswalks and the two inert scaffolds
described below *did* ship; the loader, the staging projection and the family
work items did not. See <<what-shipped>> before you trust any "we will" in the
rest of this page.
====

== Goal

Take documents from "application-subset crosswalk only, unconsumed" to: all
in-scope source families mapped to a valid DEMOS type, fail-closed validated,
SME and David signed, and consumed by a metadata-only `demos_app.document`
loader. Real file blobs and S3, `deliverable_action` (state-2 submission
linkage), and the full `reference` loader were explicitly deferred.

Only the first clause was ever reached, and even that only for two families.

== Grounded target contract

The spec pinned the DEMOS DDL snapshot `30c6ee7c...`. That pin has since moved:
`reports/prisma_ddl.sha256` now points at `a4dd0db9...b217d6a9f3`, and
`state/prisma_ddl/` holds both snapshots. Every contract claim below still holds
against the current pin.

* `document` NOT NULL columns: `id`, `name`, `s3_path`, `owner_user_id`,
  `document_type_id`, `application_id`. Nullable: `phase_id`, the deliverable
  linkage columns, and `description`.
* Composite FKs force legal combinations. `document(phase_id, document_type_id)`
  references `phase_document_type`, and
  `document(deliverable_type_id, document_type_id)` references
  `deliverable_type_document_type`. `document_type` and both junction tables are
  Prisma-seeded (see `state/prisma_seeded_tables.json`), so a mapping must
  target a seeded value that is also legal in its phase or deliverable-type
  context.
* Three-state deliverable routing is enforced by
  `check_deliverable_null_states` and `no_submitted_deliverable_cms_files`; see
  xref:reference-cross-cutting-derivations.adoc#document-source-families[document
  source families] for the same contract in the derivation reference.
* `check_non_empty_s3_path` applies to `document` and `reference`.
  `document_pending_upload` is the only document variant without an `s3_path`
  column.

The inert staging scaffold encodes the routing the loader would have had to
produce:

[cols="1,2,2"]
|===
| State | Condition | Required column values

| 1 non-deliverable
| `deliverable_id IS NULL`
| all `deliverable_*` columns NULL; `check_deliverable_null_states` forces `is_cms_attached_file = NULL` (not false) and `submission_action_id = NULL`

| 2 state-submitted
| linked, plus a state submission action
| `is_cms_attached_file = false`, `submission_action_id = <deliverable_action id>`

| 3 cms-attached
| linked, plus a CMS-attached file
| `is_cms_attached_file = true`, `submission_action_id = NULL`
|===

== Resolved decisions

[[d1]]
=== D1 (2026-07-16): deliverable status source = `mdcd_dlvrbl.mdcd_dlvrbl_crnt_stus_cd`

Deliverable status is sourced directly from
`mdcd_dlvrbl.mdcd_dlvrbl_crnt_stus_cd` (ref `mdcd_dlvrbl_stus_rfrnc`). The
BN-file "acceptance status" is not used, and
`mdcd_dlvrbl_fil_doc.upld_aftr_acptd_ind` is not a tie-breaker between the two.

Evidence, from the read-only source profile over live rows:

* Acceptance status (`mdcd_dlvrbl_acptnc_stus_cd`) is BN-only. It is referenced
  by a single table, `bdgt_ntrlty_fil_doc_stus`; all 1,771 acceptance rows
  (1,302 distinct files) resolve to `bdgt_ntrlty_fil_ind=1` files (0 monitoring,
  0 non-BN). BN is retired and DEMOS-owned, so acceptance status is out of scope.
* `upld_aftr_acptd_ind` does not align with acceptance status: of 499 live files
  with the flag set, 466 (93%) are non-BN (no acceptance status) and only 33 are
  BN. Just 3 files have the flag set plus both a deliverable status and an
  acceptance status, so there is no meaningful tie to break.
* The two enums are disjoint vocabularies (deliverable status 17 values,
  acceptance status 7 values) and never agree by name (0 matches; the dominant
  pair is "Accepted" / "Past Due"). They also reuse integer codes with different
  meanings: code `6` is "Accepted" for deliverable status but "Past Due" for
  acceptance status. They must never be compared by raw code.

Relating acceptance status to a deliverable must bridge through the file
(`bdgt_ntrlty_fil_doc_stus.mdcd_dlvrbl_fil_doc_id` ->
`mdcd_dlvrbl_fil_doc.mdcd_dlvrbl_id` -> `mdcd_dlvrbl.mdcd_dlvrbl_id`), not by
equating a file id to a deliverable id. Bridged correctly, the 1,302 BN files
with acceptance status span 1,078 deliverables.

[[d2]]
=== D2 (2026-07-17, David): untyped deliverable files default to "General File"

DEMOS deliverables only carry general files, so the roughly 85% of live files
with no `fil_doc_cd` and no type flag default to the DEMOS *General File* type.
David notes it is unlikely that all of them are truly general files, so the
migration must allow for later corrections; the crosswalk CSV is the correction
point and post-migration reclassification is expected. See <<d7>>: the parent
deliverable (type plus name), not the sparse file-level tag, is the richer
classifier and the recommended basis for that reclassification.

[[d3]]
=== D3 (2026-07-17, David): BN-flagged deliverable files are out of scope

The 1,613 live files with `bdgt_ntrlty_fil_ind=1` are out of scope, consistent
with the retired, DEMOS-owned budget-neutrality machinery. They are excluded
from the deliverable-file loader.

[[d4]]
=== D4 (2026-07-17, David): owner fallback = Primary Project Officer, DDME for M&E

When the source uploader (`user_id`) is not in the migrated users,
`owner_user_id` falls back to the demonstration's Primary Project Officer. For
monitoring and evaluation deliverables, prefer the demonstration's DDME when
available.

[[d5]]
=== D5 (2026-07-17, source-derived): `cmt_orgn_cd` on the file table is file origin

`mdcd_dlvrbl_fil_doc.cmt_orgn_cd` is the file-origin signal David described:
`S` = state-attached, `C` = CMS-attached. The PMDA application source is not
available in this environment, so this was reverse-engineered from the source DB,
which is authoritative. Cross-tabbing origin against the uploader's PMDA role
(`user_role_asgnmt` -> `role_rfrnc`) on live rows: `S` files are uploaded by the
`State User` role in 12,368 of 12,388 cases (99.8%); `C` files are uploaded by
CMS or federal-side roles (CMS Project Officer, CMS Technical Director, DDME
Analyst, Monitoring/Financial Lead, Internal Administrator) in 347 of 348 cases
(99.7%). Only S and C occur.

CAUTION: This is a different concept from the same-named `cmt_orgn_cd` on the
comment table (`mdcd_dlvrbl_cmt`), which has a six-value domain
`+{A,B,C,I,R,S}+` routing to private or public visibility. Same column name, two
tables, two meanings; the `cmt_` prefix on the file column is a naming trap.

The loader would route `C` -> state 3 (CMS-attached) and `S` -> state 2
(state-submitted).

[[d6]]
=== D6 (2026-07-17, source-derived): `fil_doc_cd` mirrors the type flags 1:1

The populated `fil_doc_cd` values align with the boolean type flags on live rows,
so they carry no information beyond the flags and collapse to three DEMOS
meanings:

* `1` corresponds to `bdgt_ntrlty_fil_ind=1` (Budget Neutrality), 1,537 files,
  excluded per D3.
* `2` and `3` correspond to `mntrg_rpt_fil_ind=1` (Monitoring Report),
  90 + 189 = 279 files, folding to one DEMOS "Monitoring Report" type. Code `2`
  additionally carries `proc_mntrg_rpt_ind` on 37 rows; both variants collapse.
* `7` and `9` correspond to `mntrg_prtcl_fil_ind=1` (Monitoring Protocol),
  28 + 34 = 62 files, folding to one DEMOS "Monitoring Protocol" type. Protocol
  report versus workbook collapse, which was exactly David's example.
* NULL or no flag maps to General File (D2 default).

Every typed file is `cmt_orgn='S'` (state-submitted); all 348 CMS-attached files
are untyped. The only remaining dependency was confirming the Monitoring Report
and Monitoring Protocol DEMOS types are legal per
`deliverable_type_document_type` (David seed-legality item).

This is the one decision whose target artifact exists.
`reports/crosswalks/deliverable_file_type.csv` carries five rows: code `1`
(Budget Neutrality file) with an empty `demos_text_id` and `in_scope=false`,
codes `2` and `3` both to `Monitoring Report`, and codes `7` and `9` both to
`Monitoring Protocol`, all three `in_scope=true`. NULL carries no row at all,
because it is not a source code.

The seed-legality dependency was closed in the same crosswalk. Its header
records:

[source,sql]
----
 * The collapse targets are legal for their monitoring deliverable types in the
 * DEMOS seed: ('Monitoring Report','Monitoring Report') and
 * ('Monitoring Protocol','Monitoring Protocol') both exist in
 * deliverable_type_document_type (see reports/prisma/seeded/). Composite-FK
 * legality per row is enforced at load time against the deliverable's own type;
 * where a typed file sits on a non-monitoring deliverable the loader falls back
 * to General File (universally legal).
----

WARNING: The "1:1" claim in this decision is *not* safe as a filter. A 2026-07-27
re-probe found 1,872 rows carrying `bdgt_ntrlty_fil_ind = 1` with a NULL

files as General File, violating repo-wide BN scope; both signals must be
excluded. The spec's own numbers already implied this, since 1,613 BN-flagged
live files minus 1,537 files at code `1` leaves exactly 76. A further 8 rows, all
soft-deleted, carry `mntrg_rpt_fil_ind = 1` with a protocol code. See
<<out-of-scope>>.

[[d7]]
=== D7 (2026-07-17, source-derived): the "General File" files are typed by their deliverable

The file-level type (`fil_doc_cd` or the boolean flags) is applied to only about
15% of live files. The roughly 10,782 untyped files are not genuinely
uncategorized; they are substantive deliverable documents that were simply never
tagged. Three independent signals agree, from the read-only source profile over
live rows.

*Parent deliverable name* is the strongest: monitoring 4,597 (43%), other reports
1,614, evaluation/design 1,351, quarterly reports 1,305, annual reports 780,
plans 233, protocols 174, interim/summative eval 73, STC/terms 46,
budget-neutrality reports 30, extension/amendment/waiver 47. Only about 527 (5%)
are uncategorizable by deliverable context.

*File format*: the real extension is in `doc_name`. `dlvrbl_fil_name` is
`doc_name` plus a version suffix such as `.0`, which garbles naive extension
parsing. Counts: pdf 4,811 (45%), docx 2,877 (27%), xlsx 2,498 (23%), xlsm 300,
zip 161, xls 79, doc 40. That is about 72% narrative documents and about 26%
spreadsheets.

*File name*: names are explicit, for example
`1115 Waiver Monitoring Report Q2 Final.pdf`,
`OK_SMI-DY3Q2_Report_Part-A_20230829.xlsx`, and
`... Summative Evaluation Report_Final...pdf`. They are often clearly monitoring
or evaluation despite no file-level tag.

Implication: "General File" (D2) is a defensible day-one default but a lower
bound that masks real categories. Context is preserved through the deliverable
link, so nothing is lost. The recommended reclassification path (the D2
correction point) is to derive `document_type` from the parent deliverable's type
and name plus filename heuristics, for example `Report_Part-A` -> monitoring
report workbook, which is far richer than the sparse `fil_doc_cd`.

Two edges:

* The parent deliverable type-code space (`mdcd_dlvrbl_type_cd` values `0` and
  `50`--`88`) does not resolve against `mdcd_dlvrbl_type_rfrnc` (codes `1`--`8`;
  code `8` is "Demonstration Specific"), so a fuller deliverable-type reference
  must be located, or the deliverable *name* is the authoritative label. See

* About 30 general files hang off budget-neutrality-*named* deliverables but are
  not BN-*flagged* (`bn=0`), so D3 does not exclude them and they would migrate

[[out-of-scope]]
== The 2026-07-27 out-of-scope decision

The operator decision recorded in `reports/narrative/notes.md` supersedes this
spec for `data-migration/`. A metadata-only loader targeting
`demos_app.document_pending_upload` was built and proven end-to-end (10,887
loaded, 187 held, 11,074 resolved, parity GREEN, `make constraints` clean) and
then removed. The facts that investigation established are worth more than the
code was:

* *`document_pending_upload` is a transit table, not a resting place.* Its
  resolver module exports mutations only, with no read query, and the sole exit
  is the `move_document_from_pending_to_clean(p_id, p_s3_path)` function in the
  `demos_app` schema, which copies the row into `document` and then deletes it.
  That function is driven by
  the file-process lambda after a GuardDuty scan of a real S3 object. Metadata
  parked in the pending table is invisible to every DEMOS user and would be
  destroyed by any future stale-upload cleanup.
* *`s3_path` does not have to be invented.* The file-process lambda sets its
  destination key and passes it as `p_s3_path`, so the correct value for a
  migrated document is derivable:
+
[source,text]
----
destinationKey = ${applicationId}/${documentId}
s3_path        = application_id || '/' || document_id
----
* *A byte-copy tool already exists with no producer.* The DEMOS data tool
  `migrate_files.py` copies objects between S3 buckets by reading
  `{STAGING_SCHEMA}.system_file_migration_queue (old_path, new_path, flag)`.
  Nothing in the monorepo creates or populates that table. A real document
  migration must produce it. This is the gap the scope-coverage comment names.
* *`old_path` is not recoverable from PMDA data.* `dlvrbl_fil_name` is a bare
  filename, not a path (9 of 16,214 rows contain a slash), and it is not unique
  (15,091 distinct of 16,214). The legacy bucket key layout has to come from ops.
* *The BN leak* described in the <<d6>> warning.
* *Live shape at 2026-07-27, for whoever picks this up:* 16,214 source rows;
  3,467 soft-deleted; `fil_doc_cd` NULL 13,867, `1` (BN) 1,847, `2` 131, `3` 268,
  `7` 48, `9` 53; `cmt_orgn_cd` `S` 15,818 and `C` 396, with *zero* NULLs; and 0
  illegal `(deliverable_type_id, document_type_id)` pairs against
  `deliverable_type_document_type`. These are all-row counts, so they are not
  directly comparable with the live-only figures in <<source-profile>>.
* Both scaffolds remain correctly inert: they guard on a `stg.document_resolved`
  that no longer gets created.

The zero-NULL `cmt_orgn_cd` finding also closes ledger gap 4.4, which asked
whether routing could assume only `S` and `C` or needed a NULL default.
