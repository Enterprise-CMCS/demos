= Reference: cross-cutting PMDA derivations
:toc: left

The derivation rules that turn PMDA source columns into DEMOS migration
columns where the rule spans more than one entity: project ids, signature
levels, status and phase, soft deletes, program-detail tags, deliverable and
document routing, and the `deliverable_action` state machine. Audience: a
developer authoring or reviewing one of these derivations. By the end you will
know which rule governs each target column, whether it is built today, and
which SQL file owns it.

[IMPORTANT]
====
*Partly implemented (as of 2026-07-30).* Most of this page is shipped code;
four derivations are not, and three shipped differently from the original
2026-06-18 design. <<status,Implementation status>> is authoritative -- the
design prose below has been corrected against the tree wherever the two
disagreed.
====

== Goal

Implement cross-cutting PMDA source derivations for DEMOS migration columns,
using the `8bf725d` role-to-`person_type_id` pattern as the model: explicit
crosswalk data, staging derivation views, app loaders, and fail-closed parity
checks.

== Data-flow design

[mermaid]
....
flowchart TD
  A[PMDA schema] --> B[Crosswalks]
  A --> C[Seeds]
  B --> D[stg views]
  C --> D
  D --> E[demos_app]
  E --> F[Parity]
  F --> G[SME gates]
....

`PMDA schema` is `reports/schema_snapshot/` plus the loaded `mysql_raw`;
`Crosswalks` are the reviewed source-to-target domains under
`sql/04_crosswalks/` fed by `reports/crosswalks/*.csv`; `Seeds` are the
migration-owned static rows and limiter tables under `sql/02_seeds_static/`
and `sql/03_seeds_limiters/`; `stg views` are the deterministic derivation
layer. The original spec's second input class was an SME-supplied "sidecar",
which was never built -- seeds took its place.

== Locked decisions

[[project-ids]]
=== Project ids

*Design.* Preserve a valid `mdcd_demo_num` into
`demonstration.medicaid_id`, and `mdcd_scndry_demo_num` into
`demonstration.chip_id` when valid. Missing target-required ids block until
supplied via a validated SME sidecar keyed by
`(source_table, legacy_id, target_column)`.

*What shipped instead.* No sidecar. `medicaid_id` is always
legacy-preserved; `chip_id` is legacy-preserved when the source carries a
secondary `21-W` number and otherwise left NULL for the
`generate_medicaid_chip_id_numbers` BEFORE INSERT trigger to mint from
`demos_app.chip_id_number_seq` under `demos_app.migration_mode = 'on'`. The
loader floors that sequence above every preserved legacy `21-W` number before
inserting, so minted values cannot collide with a preserved `chip_id`. Both
values are normalized through `migration.normalize_medicaid_id` /
`migration.normalize_chip_id`, the same helpers the row-level filter uses, so
the kept set and the emitted ids never drift.

Three fail-closed or logged conditions replace the sidecar block:

* duplicate `medicaid_id` hold-back (the region-suffix-correct row wins,
  lowest legacy id breaks a tie; a group matching no member's region is held
  entirely and gates RED) --
  `sql/99_parity/14_demonstration_held_dup_medicaid.sql`;
* non-normalizable legacy `chip_id` logged for SME --
  `sql/99_parity/15_chip_id_not_normalizable.sql`;
* approved project-number collisions --
  `sql/99_parity/16_approved_project_number_collision.sql`.

The 2026-07-20 SME reconciliation recorded `chip_id` as a DEMOS-app
dependency ("loader writes NULL, DEMOS makes the column nullable"). That is
half superseded: `chip_id` is still NOT NULL in the pinned DDL and the trigger
mints it, so no nullability change is needed for the load. The
`is_migrated_from_pmda` half did land -- `sql/20_app/30_demonstration.sql`
stamps `application.is_migrated_from_pmda = TRUE`.

=== Signature levels

Corrected 2026-06-24 against the pinned Prisma DDL migration
`20260602115947_check_signature_level`:
`demonstration_signature_level_check` forces `signature_level_id` NOT NULL AND
`= 'OA'`, so the demonstration loader sets the constant `'OA'` and the
per-application PMDA code (including `OGD`) is *not* carried at the
demonstration grain. The earlier "preserve `OGD` / CHECK widening is an
external blocker" position is *superseded for `demonstration`*.

Signature-level derivation re-scopes to *amendment and extension*, whose
CHECKs allow `signature_level_id` NULL OR IN `+{OA, OCD}+`. The crosswalk maps
the PMDA code to that pair and leaves NULL when unmappable
(`sql/20_app/35_amendment.sql`: `OA -> 'OA'`, `OCD -> 'OCD'`, else NULL,
since `OGD` and `DD` are not valid amendment values). See
`reports/narrative/notes.md` (2026-06-24 pmda-scope).

`reports/crosswalks/signature_level.csv` carries five legacy codes. Code `0`
(`-- Please Select --`) is the sentinel: `null_ok=true`, and the loader
coerces an approved code-0 demonstration to `'OA'`. Code `3` (`OGD`) is
preserved in the crosswalk and the DEMOS `signature_level` seed; only the
demonstration / amendment / extension CHECKs block loading `OGD`-level rows.
Code `4` (`DD`) has no DEMOS target, stays `null_ok=false`, and fails closed
for any live approved demonstration.

=== Demonstration status code `1` (`Pending`)

Status: RESOLVED 2026-07-20 -> `Under Review` (SME: "load as Under Review and
observe"). Built. This supersedes the earlier `Pre-Submission` proposal.
`reports/crosswalks/demo_status.csv` maps all nine legacy codes; five of them
(`Extended`, `Temporarily Extended`, `Expired`, `Extension Pending`) collapse
to `Approved` because DEMOS has no stored equivalent and the distinction is a
date overlay or a separate extension entity.

=== Phase and date model

Materialize full `application_date` and `application_phase`; derive
`current_phase_id` from phase dates with a status-based fallback and parity
logging. See <<phase-date-mapping>>.

[[soft-deletes]]
=== Soft deletes

*Design.* Migrate in-scope business rows carrying `dltd_ind=1` using target
lifecycle states (for example, a deleted deliverable becomes
`status_id='Deleted'`). Drop the technical tables.

*What shipped instead.* The drop half shipped; the migrate half was
reversed. Every staging view excludes `dltd_ind = 1` outright, because
representing a soft-deleted row is a *deferred SME decision* and the loaders
do not invent one:

* `demonstration` has no target `Deleted` lifecycle state, so resurrecting
  soft-deleted demonstrations as live rows would be wrong
  (`sql/10_stg/22_demonstration_resolved.sql`);
* `amendment` likewise has no `Deleted` state
  (`sql/10_stg/33_amendment_resolved.sql`);
* whether a soft-deleted deliverable should resurrect as the DEMOS `Deleted`
  `deliverable_status` is explicitly left to SME
  (`sql/10_stg/31_deliverable_resolved.sql`).

<<soft-delete-handling>> records the corrected handling.

=== Owner and author FKs

Resolve from source `users`; block unresolved required owners.
`sql/10_stg/21_users_resolved.sql` derives each account's `person_type` from
its role assignment with an `euaId` fallback, so every row resolves a non-NULL
`person_type` and `demos_app.person.person_type_id` (NOT NULL) is satisfied
without a schema change. A deliverable whose creator did not migrate is held
back and logged.

=== Contact migration

Status: still *not implemented on current `main`*, but narrower than the
original claim. `sql/10_stg/16_filter_cntct.sql` builds demo-grain allowlists
(`stg._valid_cntct_ids`, `stg._valid_pendg_cntct_ids`) over the wide contact
anchors, fail-closed on each present role email and cascading from the
demonstration filter. What is missing is only the *contact-only `person`*
loader over `mdcd_demo_cntct` / `mdcd_pendg_demo_cntct`.

`person_state`, `system_role_assignment`, `demonstration_role_assignment` and
the primary assignment are all built -- they source from the 15 per-role
`user_id` FK columns on `mdcd_demo`, unpivoted in
`sql/10_stg/28_demonstration_role_assignment_resolved.sql`, not from the
contact tables. PMDA has no `(user, demonstration, role)` association table;
the role is fixed by the *column*, mapped through
`mysql_raw.crosswalk_demonstration_role`.

=== Program-detail tags

The 10-table mapping has been expanded to all mappable non-backup base and
pending `+*_pgm_dtl+` tables. `reports/pgm_dtl_tag_mapping.csv` now carries 69
rows covering every base `+*_pgm_dtl+` table in
`reports/schema_snapshot/table_stats.csv`, and
`reports/pgm_dtl_tag_mapping_pending.csv` carries the 68 pending
counterparts. One row (`mdcd_othr_pgm_dtl`) has a blank `tag_name` and is
SME-pending; the tag-assignment loader skips blank rows. See
<<program-detail-coverage>>.

[[bn-routing]]
=== Budget-neutrality deliverable routing

*Design.* `mdcd_dlvrbl.bdgt_ntrlty_ind` authoritative;
`bdgt_ntrlty_fil_ind` creates workbook rows; semi-annual BN (type 5/6 plus
`bdgt_ntrlty_ind=1`) routes to Quarterly BN.

*Superseded on two counts.* Post-load verification against
`mysql_raw.mdcd_dlvrbl` overturned both premises (see the correction banner in
`reports/crosswalks/proposed/deliverable_type_bn_routing.md`):

. `mdcd_dlvrbl.mdcd_dlvrbl_type_cd` is not the coarse cadence code. It
  carries the rich report-occurrence vocabulary
  (`mdcd_dlvrbl_rpt_ocrnc_rfrnc`): 40 of 40 distinct live type codes resolve
  against it and 0 of 40 against `mdcd_dlvrbl_type_rfrnc`. Codes `57`
  (Quarterly BN) and `70` (Annual BN) are already carried per deliverable.
. There is therefore *no BN matrix and no second routing input*.
  `deliverable_type` is a single-input direct map
  (`reports/crosswalks/deliverable_type.csv`,
  `sql/04_crosswalks/52_deliverable_type.sql`, fail-closed check
  `53_deliverable_type_check.sql`). `bdgt_ntrlty_ind` was retired as a routing
  input and kept only as a non-gating QA signal in
  `sql/99_parity/43_deliverable_bn_qa.sql`, which flags every row where the
  type-based classification disagrees with the legacy flag or the free-text
  name.

The semi-annual question is moot under a direct map: legacy code `6`
(Semi-Annually) and `54` (Semi-Annual Monitoring Report) both route to
`Monitoring Report` on cadence collapse, with the period surviving as
`due_date`; code `6` is seen only on soft-deleted deliverables.

Budget neutrality itself is out of scope (SME decision 2026-07-16): DEMOS
owns it, users upload v2.14 workbooks into DEMOS, and the migration builds no
BN aggregate. `bdgt_ntrlty_fil_ind` (`fil_doc_cd = 1`) is excluded from the
document crosswalk with a NULL target and `in_scope=false`
(`sql/04_crosswalks/71_deliverable_file_type.sql`).

=== Document routing

Source family, then explicit flags, then a type-code crosswalk. See
<<document-source-families>>.

=== `mdcd_demo_type_cd`

Scoped metadata only. The canonical demonstration-type tags come from the
program-detail rows, not from this column. Its one consumer is the
reference-material fold, where `rfrnc_matl.mdcd_demo_type_cd` is resolved
data-backed against its own source lookup `mysql_raw.mdcd_demo_type_rfrnc`
(61 of 63 codes are identity matches with `demos_app.tag_name.id`).

=== Reference materials

*Design.* Map `rfrnc_matl` to `reference` plus `reference_tag_assignment`
where crosswalkable.

*Corrected target.* The demonstration-type vocabulary lives in the
`Demonstration Type` tag_type (`demos_app.demonstration_type_tag_type_limit`),
so the correct target is `demos_app.reference_demonstration_type`, *not*
`reference_tag_assignment` -- the latter is restricted to the `Reference`
tag_type, of which only one tag (FAQ) is seeded. The associative fold is
authored (`sql/21_app_associative/20_reference_demonstration_type.sql`) and
reuses the same 61-tag vocabulary as the demonstration fold, but stays inert:
`sql/05_id_maps/14_rfrnc_matl.sql` creates
`migration._id_map_rfrnc_matl` empty and no `rfrnc_matl -> demos_app.reference`
loader exists yet (it needs an owner user / person-type FK decision). Codes
`0` (Not Applicable) and `OTHR` (Other) are not seeded tags and fall out of
the JOIN, reported as skipped.

(`ApplicationReceived`, `ApplicationSubmitted`, `Phase2Received`,

[[document-linkage]]
== Document-to-deliverable linkage routing

DEMOS migration `20260623125420_no_deliverable_submitted_cms_files`, mirrored
into the pinned Prisma DDL `state/prisma_ddl/<sha>.sql` (pinned via
`reports/prisma_ddl.sha256`), finalizes a three-way routing rule for every
migrated `demos_app.document` row. Its intent is that a file *attached by CMS*
to a deliverable can never simultaneously be recorded as a *state submission*:
the migration first runs
`UPDATE demos_app.document SET deliverable_submission_action_id = NULL WHERE deliverable_is_cms_attached_file = TRUE`,
then adds the guard CHECK below. The constraint name reorders the words --
migration `20260623125420_no_deliverable_submitted_cms_files`, constraint
`no_submitted_deliverable_cms_files`.

The relevant `document` columns, all nullable, are `deliverable_id` (UUID),
`deliverable_type_id` (TEXT), `deliverable_is_cms_attached_file` (BOOLEAN),
`deliverable_submission_action_id` (UUID) and
`deliverable_submission_action_type_id` (TEXT). Two CHECK constraints jointly
fix the legal combinations.

`check_deliverable_null_states` ties the deliverable columns together as
all-absent or linked:

[source,sql]
----
CHECK (
    (deliverable_id IS NULL
        AND deliverable_type_id IS NULL
        AND deliverable_is_cms_attached_file IS NULL
        AND deliverable_submission_action_id IS NULL
        AND deliverable_submission_action_type_id IS NULL)
    OR
    (deliverable_id IS NOT NULL
        AND deliverable_type_id IS NOT NULL
        AND deliverable_is_cms_attached_file IS NOT NULL)
);
----

`no_submitted_deliverable_cms_files`, new in `20260623125420`, forbids a
CMS-attached file from carrying a submission action:

[source,sql]
----
CHECK (
    NOT (deliverable_is_cms_attached_file = true AND deliverable_submission_action_id IS NOT NULL)
);
----

[NOTE]
====
`demos_app.document_infected` carries its own, narrower
`check_deliverable_null_states` covering only the first three columns. The
five-column form quoted above is the one on `demos_app.document`.
====

Together these route every `document` row into exactly one of three states:

. *Non-deliverable document*: not linked to any deliverable
  (`deliverable_id IS NULL`). `check_deliverable_null_states` then forces
  `deliverable_is_cms_attached_file IS NULL` and
  `deliverable_submission_action_id IS NULL` -- the flag is NULL, not `false`.
. *State-submitted deliverable document*: linked to a deliverable and
  submitted by a state user. `deliverable_is_cms_attached_file = false`;
  `deliverable_submission_action_id` points at the submitting
  `deliverable_action` row. Permitted by
  `no_submitted_deliverable_cms_files` because the CMS-attached flag is false.
. *CMS-attached deliverable file*: linked to a deliverable but attached by
  CMS rather than submitted by the state.
  `deliverable_is_cms_attached_file = true`, so
  `no_submitted_deliverable_cms_files` requires
  `deliverable_submission_action_id IS NULL`.

[cols="3,^1,^2,^3"]
|===
| State | `deliverable_id` | `deliverable_is_cms_attached_file` | `deliverable_submission_action_id`

| Non-deliverable document
| `NULL`
| `NULL` footnote:nondel[Per `check_deliverable_null_states`, a
non-deliverable document carries `deliverable_is_cms_attached_file = NULL`,

  `deliverable_submission_action_id` via the composite FK
  `document(deliverable_submission_action_id, deliverable_submission_action_type_id) -> deliverable_action(id, action_type_id)`,
  and is independently FK-limited to the single seeded submission action type.
  It is NULL in states 1 and 3.

[[deliverable-action]]
== The `deliverable_action` state-machine derivation

The `deliverable_action` loader synthesizes the per-deliverable workflow
events DEMOS would otherwise create at runtime. *The pinned DDL seeds no
`deliverable_action` rows* -- every `demos_app.deliverable_action` statement is
an `ALTER TABLE ... ADD CONSTRAINT`, never an `INSERT`. It seeds only the
supporting domains, so the loader derives the event rows from the legacy
deliverable source.

What the DDL does seed:

* `deliverable_action_type`: the action-name domain, `id` plus four boolean
  flags, 14 rows reproduced verbatim in <<deliverable-action-types>>.
* `deliverable_action_configuration`: the legal state machine, as
  `(action_type_id, old_status_id, new_status_id)` triples.
* `deliverable_submission_action_type_limit`: exactly one row,
  `('Submitted Deliverable')`.
* the `deliverable_status` domain, 8 ids: `'Upcoming'`, `'Past Due'`,
  `'Submitted'`, `'Under CMS Review'`, `'Accepted'`, `'Approved'`,
  `'Received and Filed'`, `'Deleted'`.

=== State machine

`deliverable_action_configuration` enumerates the allowed
`(action_type_id, old_status_id -> new_status_id)` transitions over the
`deliverable_status` domain; every derived `deliverable_action` row must match
one seeded triple. The submission action's transitions are:

[source,sql]
----
('Submitted Deliverable', 'Upcoming', 'Submitted'),
('Submitted Deliverable', 'Past Due', 'Submitted'),
('Submitted Deliverable', 'Submitted', 'Submitted'),
('Submitted Deliverable', 'Under CMS Review', 'Submitted'),
----

=== Submission-linkage contract

`document.deliverable_submission_action_id` references the specific submission
`deliverable_action` for a deliverable through the composite FK
`document(deliverable_submission_action_id, deliverable_submission_action_type_id) -> deliverable_action(id, action_type_id)`.
The accompanying `document.deliverable_submission_action_type_id` is
FK-constrained to `deliverable_submission_action_type_limit`, which the DDL
seeds with the single value `'Submitted Deliverable'`. The referenced action's
`action_type_id` must therefore be exactly `'Submitted Deliverable'`; no other
action type can be a document's submission action.

=== Per-row integrity a loader must satisfy

Verbatim CHECK constraints on `demos_app.deliverable_action`:

* `block_unpermitted_due_date_changes`:
  `NOT (due_date_change_allowed = FALSE AND old_due_date != new_due_date)`
* `check_non_empty_note`: `(note IS NULL OR trim(note) != '')`
* `require_extension_id_for_extension_actions`:
  `(extension_id_optional = TRUE) OR (extension_id_optional = FALSE AND active_extension_id IS NOT NULL)`
* `require_notes_for_user_actions`:
  `(should_have_note = FALSE AND note IS NULL) OR (should_have_note = TRUE AND note IS NOT NULL)`
* `require_user_id_for_user_actions`:
  `(should_have_user_id = FALSE AND user_id IS NULL) OR (should_have_user_id = TRUE AND user_id IS NOT NULL)`

The four boolean flags on each row are not free: they must equal the seeded
`deliverable_action_type` row for that `action_type_id`, via the composite FK
`deliverable_action(action_type_id, due_date_change_allowed, should_have_note, should_have_user_id, extension_id_optional) -> deliverable_action_type(...)`,
and `(action_type_id, old_status_id, new_status_id)` must exist in
`deliverable_action_configuration`. `deliverable_id -> deliverable`,
`user_id -> users` and `active_extension_id -> deliverable_extension`
complete the FK shape.
